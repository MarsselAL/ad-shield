## A2. Cause of the delay today (what is known)
1. CHECKED (our own measurement, docs/DESIGN-v2.md:110-126): SABR first videoplayback answer carries an ad context (type 5 update), a snackbar message and NEXT_REQUEST_POLICY backoff 4.0-8.8 s. A client that plays the ad hides the wait; a client whose ad data is pruned shows a black 0x0 player. Fix = params oAEBogYBLg (response without ad keys, no backoff).
2. CHECKED (results/*bd-*, 2026-11-21, anonymous headless Chrome 158, time to first frame): current build 1.6-2.3 s; without DNR pp rule (bd-nodnr) 5.5-11.5 s; with no scriptlet body edit but DNR (bd-nobody) 1.8-2.2 s; no pruning/edit at all (bd-none) 5.8-14.1 s; no extension: first-frame metric empty, but t=1.8 s at the 3 s mark (about 1.0 s start). So the pp redirect is what cuts the delay on direct loads; floor gap to "no extension" is about 0.5-1 s.
3. CHECKED (rules/scriptlets.json youtube "about", our 11-22 measure): with the block-screen guard, 3 videos began playing 2.5 s, 6.1 s, 6.2 s after navigation start (8.7 s before). The 6 s cases are the likely source of a user-visible 3-5 s wait. INFERRED: they come from the enforcement swap (about 1.4 s after navigation) plus the recover/reload path, not from the hooks.
4. REPORTED (uBO code, quick-fixes L25): uBO's own cost sources are a MutationObserver on document subtree calling a player-state check on every mutation, proxies on Map.prototype.has, Array.prototype.push and Promise.prototype.then, and one player reload per failed tag. No public report blames hook cost for delay; the 11-21 uBO threads blame account-based fake buffering. We already removed these hooks (DESIGN-v2).
5. uBO SSAP: when getStatsForNerds().debug_info starts with "SSAP, AD" uBO calls player.seekTo(duration) (REPORTED, from reading L25; the "!startsWith SSAP" branch returns early, the SSAP case falls through to seekTo). AdGuard #246850 (11-10) "3-4 ads per video" was auto-closed by bot as first-party ads.

## A3. Likely delay sources in OUR code (all INFERRED unless stated)
Order = my estimate of impact for a logged-in profile.
1. src/scriptlets/lib.js:1561-1577 (youtubePlayabilityRecover.step) + constants 1314-1324. The fallback reload (loadVideoById) waits for `doc.readyState === 'complete' || j.cued` (1561), then RECOVER_SETTLE_TICKS=3 consecutive 100 ms ticks (0.3 s, 1577), tick 100 ms (1315). On a heavy page `load` can come 2-4 s after navigation start, so a flagged session that needs the reload pays that wait. Cut: reload as soon as player state is -1/5 and the response is enforced (j.cued already exists), SETTLE 3 -> 1, event-driven on yt-player-updated instead of polling.
2. rules/scriptlets.json youtube: only tag oaeb, no stalled-start detector. If a flagged account still gets backoff (state 3, resolution 0x0, buffer_health 0.00 s for more than about 2 s, no ad-showing), nothing happens; the player waits the 4-9 s. uBO's answer is reload with the next tag. Cheap version without uBO's Map/Array/Promise hooks: reuse the 100 ms tick of youtube-playability-recover to read player.getStatsForNerds() (resolution "0x0", buffer_health_seconds "0.00 s") and call loadVideoById(id, start) once with a second body variant (oaeb stays first; fallbacks from experimental list: inline = contentPlaybackContext.isInlinePlaybackNoAd:true; yaf4 = params YAF4AaIGAS4). Needs a mutable "current tag" read by edit-request-body (lib.js:598-684, edits are static strings today, scriptlets.json lines for the two edit-request-body entries).
3. src/scriptlets/lib.js:1056 `if (!isSsap(player))` + MAX_SEEK_AD=90 (1020): SSAP stitched ads are never skipped; they play to the end. uBO seeks them with player.seekTo(duration). Our own docs say seeks froze 1.1.x (DESIGN-v2:135), so test seekTo(duration) on SSAP only, once per ad, behind the existing guards.
4. Embeds: scriptlets.json youtube hosts include youtube-nocookie.com (rules[0].hosts) but edit-request-body requires clientName "WEB" with attestationRequest; embed clients are WEB_EMBEDDED_PLAYER (uBO L33-35 uses serializedThirdPartyEmbedConfig + params eAFgAQ and tags channel/eafg). So embeds probably still get the backoff (embedded players on third-party pages). Add an embed edit (params eAFgAQ on /player with serializedThirdPartyEmbedConfig) and test.
5. rules/youtube.json:4 (pp on main_frame /watch? only): not a delay source (measured as the fix), but /shorts/, /live/ and youtu.be paths that do not match `|https://www.youtube.com/watch?` take their first response from the HTML without oaeb; youtu.be redirects to /watch so the rule should fire on the second hop (UNKNOWN, test). In-page entry to a video from home/search uses get_watch edit (covered).
6. Hook cost (lib.js:358 JSON.parse wrapper: up to 10 indexOf scans per parse; 389 fetch clone().text() + parse + stringify of whole /player, /get_watch, /playlist bodies before the response is handed back; 614-636 gunzip+gzip round trip of the request body on the critical path of every /player). Each is milliseconds, not seconds; the 11-21 bisect runs show no scriptlet adds measurable delay (bd-nobody 1.8-2.2 s vs cur 1.6-2.3 s). Only worth touching if profiling shows long tasks: check Chrome trace for JSON.parse wrapper on the >1 MB browse parse.
7. lib.js:845 prevent-dom-bypass wraps Node.prototype.appendChild (hot path, all appends) and :925 remove-node-text MutationObserver on the document until DOMContentLoaded. Same as uBO L88-91; low.
8. 17 s timer (scriptlets.json adjust-setTimeout "[native code]", 17000, 0.001 = 17 ms): same as uBO L55. The wrapper reads callback source only when delay==17000 (lib.js:720-735); no issue.
