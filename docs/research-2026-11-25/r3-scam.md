MV3 design (INFERRED):

- Option A: DNR dynamic/static rules for top ~30k most recent/active crypto+phishing domains (redirect to warning page).
- Option B: bundle full list as sorted hash table / Bloom/Cuckoo filter (36-bit truncated hashes of eTLD+1 and host; 500k entries ~ 1-2 MB), check in `webNavigation.onBeforeNavigate`/`tabs.onUpdated` and redirect tab to internal warning page. Needs `webNavigation` permission, no host access. Update by shipping with extension releases (privacy-first, no remote config), optionally opt-in daily fetch of a signed list from a static CDN (no user identifiers).
- Check parent domains (a.b.evil.com -> evil.com) by walking labels; use public-suffix-aware eTLD+1.

## 2. Wallet-drainer / tx protection
- Interception pattern (CHECKED for Rabby, REPORTED for Wallet Guard): content script at document_start injects page-world script that mounts/wraps `window.ethereum` (Rabby: pageProvider.js, content script via BroadcastChannel to background; CHECKED from README). Wallet Guard extension injects provider into the page and wraps send methods with a proxy (REPORTED via search summary of repo; repo licence Apache-2.0 CHECKED via API, pushed 2026-11-04).
- MV3 way: `content_scripts` with `"world": "MAIN"`, `run_at: document_start`; wrap `ethereum.request` and legacy `send/sendAsync`, plus EIP-6963 announced providers (`eip6963:announceProvider` events) since many wallets no longer rely on window.ethereum (INFERRED/known standard). Handle providers that are defined non-writable by Object.defineProperty traps.
- What to warn about without any paid API (INFERRED, local parsing of request params):
  - `eth_sign` (blind signing) -> hard warn.
  - `personal_sign` with hex that looks like a hash.
  - `eth_signTypedData_v4`: parse domain/primaryType: Permit (EIP-2612), DAI Permit, Permit2 (PermitSingle/PermitBatch/PermitTransferFrom), Seaport orders, unlimited amounts (2^256-1), far-future/zero expiration, spender not a known router.
  - `eth_sendTransaction` data selectors: approve(0x095ea7b3) with max uint, setApprovalForAll(0xa22cb465) true, increaseAllowance, transferFrom, Permit2 approve, `to` = EOA with data, `to` address on scam address list (polkadot address.json).
  - Site is on blocklist or domain is young/lookalike -> escalate.
  - Chain/`wallet_addEthereumChain`/`wallet_switchEthereumChain` oddities, `eth_requestAccounts` from flagged site.
- Needs paid/remote API: simulation of balance changes (Blockaid PPOM, Wallet Guard API, Pocket Universe, Fire). Wallet Guard API endpoint exists at docs.walletguard.app (REPORTED). Wallet Guard acquired by Consensys; Pocket Universe and Fire acquired by Kerberus (REPORTED, one summary; not verified).
- Licences: Rabby = MIT with brand/logo reserved (CHECKED, LICENSE file; GitHub shows NOASSERTION) -> reusable code, not brand. Wallet Guard ext = Apache-2.0 (CHECKED API) -> reusable w/ attribution/NOTICE. MetaMask core MIT (CHECKED). MetaMask ppom-validator: no licence file found at main/LICENSE (404, CHECKED) and the Blockaid ruleset is proprietary (INFERRED) -> do not reuse. Pocket Universe: open-source status not found (UNKNOWN). Scam Sniffer extension: not examined (UNKNOWN).
- Scope caution: AdBrake is not a wallet; warnings only, never block silently; let the user continue. Injecting into MAIN world on all pages touches privacy/perf: restrict to pages where a provider exists (inject lazily: only wrap when `window.ethereum` or EIP-6963 event appears).
- Evidence of effectiveness: vendor claims only (INFERRED: none independently verified). Known limit: simulators miss multi-step/time-delayed drains (REPORTED, ryder.id article title only).

## 3. Lookalike / homograph
- Techniques (INFERRED, standard): (a) punycode `xn--` decode + flag mixed-script labels (UTS #39 restriction levels, confusables skeleton via confusables.txt from Unicode, Unicode licence permissive); Chrome already does IDN spoof checks (INFERRED), so value-add is crypto brand targets. (b) Skeleton compare: map confusables (rn->m, vv->w, 0->o, 1->l/i) then compare to protected brand list. (c) Damerau-Levenshtein distance <=1 for labels length >=6 (eth-phishing-detect uses tolerance=1 against a short fuzzylist; CHECKED values, algorithm details INFERRED: Levenshtein on the hostname vs fuzzylist). (d) Keyboard-adjacent substitution (QWERTY neighbour map), adjacent transposition, omitted/doubled char, TLD swap (.com->.co/.io). (e) Combosquatting: brand token + keyword (support, wallet, airdrop, claim, verify, login, connect, helpdesk, recover, validate, sync) in label separated by '-' or concatenated, or brand as subdomain of unrelated domain (metamask.io.evil.xyz).
- Data structure: protected-brand list of ~300 (exchanges, wallets, DeFi, top bank/tech brands, from Tranco top sites subset) -> precomputed skeleton set in a Map; per navigation: eTLD+1 -> skeleton -> exact hit in Set (O(1)); for edit-distance-1 use "deletion neighbourhood" (SymSpell): store all single-deletion variants of brand labels in a hash set (~300*12 entries) and probe the candidate's deletions. Combosquat: tokenize label on '-' and substring-scan with Aho-Corasick or plain `includes` over 300 brands (sub-millisecond). All in MV3 service worker, no network.
- FP risk: high for short brands and for legitimate sibling domains (e.g. metamask.io vs. consensys.net). Mitigate: allowlist of official domains per brand (eth-phishing-detect whitelist is a model, CHECKED structure), min label length, only warn (not block), require crypto context (page contains wallet-connect UI or provider) before raising severity, suppress if domain in Tranco top 100k.

## 4. Fake support, fake update, ClickFix, clipboard swap
- ClickFix: fake CAPTCHA/"verify you are human" page writes a PowerShell/mshta/curl command to the clipboard, tells user to press Win+R/Ctrl+V/Enter. 2026 variants: CrashFix (Microsoft, 2026-02-05, REPORTED), TerminalFix (Malwarebytes 2026-09), ConsentFix, server-side polymorphism (Menlo) (all REPORTED from search listing; not opened). Vendors (Push Security, Check Point) detect in-browser by page behaviour + clipboard content analysis (REPORTED, vendor blogs, self-interested).
- Extension feasible detection (INFERRED): content script in MAIN world hooks `navigator.clipboard.writeText` and `document.execCommand('copy')` and `ClipboardEvent` `setData`; when a page writes text matching command patterns (powershell, `-enc`, `iex`, `mshta`, `cmd /c`, `curl|bash`, `certutil`, `msiexec`, `Invoke-WebRequest`, base64 blobs, "Win+R", "verification ID") without a user selection of visible code, show a warning banner and optionally replace clipboard with empty string/warn. Combine with DOM heuristics: text like "I'm not a robot", "Press Win+R", "Ctrl+V", "Verify" + clipboard write in click handler. Low cost, no data needed, FP risk: developer sites (legit "copy command" buttons on docs/GitHub/Homebrew) -> only fire when the page also has a fake-captcha/verification context or the domain is not an allowlisted dev docs site; keep a prompt not a hard block.
- Fake browser-update / tech-support: heuristics: full-screen/ fullscreen API abuse + phone number + "Microsoft Defender/Windows warning", `beforeunload` traps, repeated alert()/history.pushState loops, fake "Chrome update" download of .exe/.msi/.dmg from non-vendor host. DNR: block/ warn on `download` from untrusted domain pages is hard; use `chrome.downloads.onDeterminingFilename` (needs downloads perm) to warn on executables from pages claiming to be updates (INFERRED).
- Clipboard address swap (malware on OS, not web): extension can't see OS clipboard; it can: (1) on copy events in page, record address copied and on paste into inputs on same page compare (content script `paste`/`input` events); warn on mismatch of first4/last4 (address poisoning); (2) wallet-address poisoning check: warn when pasted address matches a recent-history address by prefix/suffix but differs in middle (INFERRED, known attack pattern). Needs local history of addresses only in session memory.
- Evidence: UNKNOWN for any extension's measured efficacy; no independent study found.

## 5. Privacy-preserving lookups
- Best default: no online check; shipped local filter (see section 1).
- If online: Safe Browsing style hash-prefix (k-anonymity): send first 4 bytes of SHA-256 of canonicalized host, receive all full hashes with that prefix, compare locally. Google's own v4 Update API/v5 URL (hashes.search) pages could not be fetched (404), so v5 specifics UNKNOWN. Chrome's built-in already uses its own mechanism, and Safe Browsing API use terms restrict commercial use (REPORTED/INFERRED).
- Self-hosted alternative: static CDN with sharded files by 2-byte hash prefix (65k shards, or 4k by 12 bits); client fetches the shard for the prefix only -> server learns only 12-16 bits. Cacheable, no logs needed (INFERRED, design). Also cheaper than an API.
- Must be opt-in and documented since AdBrake claims "no telemetry, no remote config".
